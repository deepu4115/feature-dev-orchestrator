# Feature Dev Orchestrator Enhancement Notes

## Overview
This document captures the issues encountered while using the feature-dev orchestrator in the Ecommerce workspace. The goal is to make the orchestrator smoother, more predictable, and more CLI-driven so that agents can rely on commands and structured validation instead of reverse-engineering the schema or reading external implementation files.

The main theme from this experience is: the orchestration system was usable, but not smooth enough for an agent-first workflow. The biggest problems were schema discovery, unclear validation contracts, and too much manual reconstruction of required planning files.

---

## Executive Summary
The experience surfaced several issues that made the workflow feel brittle:

1. The CLI did not clearly expose the exact JSON schema for tasks and planning bundle files.
2. Validation errors did not clearly explain the required structure early enough.
3. Draft bundle files had to be reconstructed manually after failing validation.
4. The task validation step failed due to schema mismatches that could have been caught earlier.
5. The workflow forced agent-side reverse engineering, including reading the feature-dev source tree outside the current workspace.
6. The approval and review flow was valid, but too much of the process depended on trial-and-error.
7. The CLI should provide canonical templates and examples so agents can work only through CLI-driven commands.

---

## Detailed Issues Faced

### 1. Missing discoverability of the task schema
The largest issue was the lack of a clear canonical schema for tasks.json.

The expected shape for tasks was not obvious from the CLI experience alone. The workflow started with a task list generated by commands, but the task objects still had to be corrected after validation. The result was wasted effort and uncertain structure.

What should have happened:
- feature-dev should expose a template or example for .feature/tasks/tasks.json
- the CLI should show required fields and their types
- the tool should validate the structure before the user ever tries to submit,
- or it should allow creation from a built-in template that is already valid

What actually happened:
- the task file was created with a plausible structure
- validation later failed because field types did not match CLI expectations
- the schema had to be deduced by inspecting validation output and external source files

This is a strong sign that the CLI contract was not discoverable enough for agent use.

---

### 2. Unexpected JSON schema mismatch during plan submission
The first major blocker was this validation error:

- cannot unmarshal string into Go struct field .0.verification of type []VerificationStep

This mismatch meant that each task's verification field was expected to be an array of objects, but the task file used a string format.

This is not a business-domain problem; it is a workflow/tooling problem.

The real issue is that the CLI accepted a task file that was close to valid, but not actually valid according to its own schema. The user/agent is forced to discover the exact field contract only through failure messages.

Expected behavior:
- the CLI should provide a `feature-dev task add --help` or template output that demonstrates the exact structure for `verification`
- the task creation flow should generate a valid object shape automatically

Actual behavior:
- the generated tasks file must be corrected manually after validation errors

---

### 3. Draft planning bundle shape was not obvious
The draft bundle under `.feature/plans/draft/` also needed to be shaped correctly. The files included:

- requirements.json
- assumptions.json
- risks.json
- impact.json
- repo-analysis.json

Each one had to be wrapped in the expected top-level object format that the validator accepts.

For example:
- requirements.json had to be a JSON object with a `requirements` array
- assumptions.json had to be an object with an `assumptions` array
- risks.json had to be an object with a `risks` array
- impact.json had to be an object with an `impact` array
- repo-analysis.json had to be an object with a `repositories` array

This was a significant friction point because the files looked reasonable as raw JSON arrays at first glance, but the validator expected wrapper objects.

This indicates a missing contract surfaced to the user.

---

### 4. Validation failures arrived too late and were not precise enough
The orchestrator should guide the user before they get too far into the workflow. Instead, it failed late and with confusing errors.

Three examples from the run:

- unknown requirement id
- missing_requirements_file
- draft_bundle_load_error

These issues were partly caused by a schema mismatch and partly caused by validation happening after the task file was already created and submitted.

The problematic aspect is this: the validation was correct but not sufficiently actionable.

Better behavior would be:
- tell the agent exactly which task field is invalid
- show the canonical structure for each required file
- explain expected root keys like `requirements`, `assumptions`, `risks`, `impact`, and `repositories`
- require no external source inspection

---

### 5. Clarification mode was noisy and partially redundant
Once the plan validation failed, the CLI produced clarification questions such as:

- List the requirements extracted from PLAN.md so we can create requirements.json.
- What assumptions must be documented before implementation?
- What risks should be recorded for this plan?
- Which repositories and change areas will be affected?

These are legitimate questions, but in this case they were not the primary issue. The actual blocker was schema correctness. The tool drifted into a clarification loop before clearly telling the user that the task bundle structure was invalid.

This reduced the smoothness of the orchestration flow and made it feel less deterministic.

An improved workflow would do this instead:
- first validate the structure and schema
- then ask for missing domain-specific clarifications
- avoid asking conceptual planning questions before the structural contract is valid

---

### 6. The workflow forced agent-side reverse engineering
This was the most important issue from a tooling perspective.

To solve the validation problem, I had to inspect the external feature-dev source tree in another folder and read implementation files to discover the exact schema contract.

That means the orchestrator was not self-sufficient enough for an agent using only CLI commands and supported interfaces.

This is not the intended usage model. Agents should not need to:
- inspect external source code
- read implementation internals
- reverse-engineer Gofmt structs for JSON fields

The CLI and its documentation should be enough.

This is a real product issue because it breaks the principle of “everything should be handled by the CLI.”

---

### 7. The CLI did not provide a single canonical template for the complete planning bundle
A smooth agent workflow requires a simple, canonical template.

The expected flow should be:
- initialize workspace
- create default task template
- create default draft bundle template
- validate bundle
- submit plan
- review plan
- approve plan
- execute loop

But in practice, that was not the experience.

Instead, the agent had to reconstruct the template by reading validation output and external code. That is high-friction and not robust.

A better orchestrator should include built-in templates such as:
- `.feature/tasks/tasks.json.example`
- `.feature/plans/draft/requirements.json.example`
- `.feature/plans/draft/assumptions.json.example`
- `.feature/plans/draft/risks.json.example`
- `.feature/plans/draft/impact.json.example`
- `.feature/plans/draft/repo-analysis.json.example`

These should be generated by the CLI and then validated automatically.

---

### 8. The task plan had to be corrected multiple times before it passed
The task DAG was revised repeatedly before validation passed.

This created a cycle of:
1. generate task entries
2. run plan submit
3. fail with schema error
4. fix task schema
5. validate again
6. fail on draft bundle shape
7. fix bundle schema
8. validate again
9. succeed

This is not “smooth orchestration.” It is a repair cycle caused by unclear contract definitions.

A good orchestrator should move the user from a valid starting state to a valid plan in one pass, not through repeated schema-debug loops.

---

### 9. The approval flow existed, but the path to get there was too brittle
The feature-dev CLI eventually reached:
- REVIEW_PENDING
- plan valid
- no runtime blockers

This is a good sign. The flow is conceptually strong.

But the path there was too fragile because it relied on manual schema reconstruction. That makes the approval flow less trustworthy in practice and harder for agents to rely on automatically.

The method should be:
- create valid tasks from CLI templates
- create valid draft files from template output
- submit from tasks
- review and approve
- proceed to execute-loop

That should be deterministic, not a debugging exercise.

---

### 10. The tooling lacked a clear “CLI-first contract” principle in practice
The feature-dev orchestrator is supposed to be command-driven. In reality, much of the intelligence was only discoverable via:
- validation messages
- external code reading
- manual JSON fix-ups

This creates a mismatch between the intended design and the actual user experience.

The tool should treat CLI commands as the source of truth, and it should provide:
- generated templates
- validation before submit
- precise field-level schema guides
- clear plan review output
- smooth approval transition

Without that, agents are still forced to reason around the tool instead of trusting it.

---

## Recovery Path That Should Exist in a Smooth Orchestrator
A better orchestrator should reduce the following pain points:

### A. Template generation
The CLI should generate valid task and draft files automatically.

### B. Schema validation before submit
The task and draft files should be validated before the plan is submitted. This should catch invalid `verification` arrays, invalid root keys, and requirement mapping issues immediately.

### C. Better error explanations
Errors should state:
- expected JSON type
- expected top-level keys
- expected object shape
- exact required files
- exact fix to apply

### D. Built-in examples and docs
A user should not need to inspect external source code. The CLI should offer example output and a generated scaffold.

### E. Deterministic agent flow
The tool should support a reliable progression:
- init
- discover
- draft bundle generation
- task generation
- validation
- submit
- review
- approve
- reconcile
- execute-loop

---

## Why This Matters
The experience showed that the orchestrator concept is strong, but the real UX issue is that the tool does not yet feel stable enough to be agent-trusted.

If an agent has to reverse-engineer a CLI’s expected JSON contract, then the process is not CLI-first and not smooth.

The command interface should be the single source of truth, and the agent should be able to proceed without file reading or implementation-source tracing.

---

## Improvement Priority List

### Priority 1: Contract and schema discoverability
- expose exact task schema
- expose exact draft bundle schema
- generate valid templates automatically

### Priority 2: Early validation
- validate before plan submit
- validate before review approval
- show precise field-level guidance

### Priority 3: Reduced clarifying noise
- ask context-specific questions only after structural validation is clean
- avoid redundant questions when the real issue is schema mismatch

### Priority 4: CLI-first workflow guarantees
- no need to inspect external repos or source trees
- no hidden assumptions about JSON structure
- no manual reverse engineering of internal structs

### Priority 5: Agent ergonomics
- one-step generation of valid tasks
- one-step generation of valid planning bundle
- predictable plan approval flow

---

## Conclusion
The issue was not that the feature-dev approach was invalid. The issue was that the workflow was not smooth enough to trust in an autonomous agent flow.

The most important gaps were:
- poor schema discoverability
- late and vague validation errors
- manual reconstruction of required drafts
- need to inspect external source code for contract details
- noisy clarification loops before structural issues were resolved

These should be treated as explicit orchestrator improvements before further agent-driven usage is expected to be smooth.
